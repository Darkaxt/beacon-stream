# Beacon Hosted Emulator Stream Acceptance Design

Status: approved Gate 5 architecture-recovery slice, 2026-07-14

## Purpose

Beacon's hosted Android job proves JNI loading, StreamCore lifecycle, callback threading,
MediaCodec support, and `SurfaceView` lifecycle. The server-dependent instrumentation tests are
currently skipped because the Ubuntu emulator job has no Windows Beacon host. This leaves the
Gate 5 wire-to-screen acceptance requirement unproven.

This slice adds a test-only Beacon endpoint inside the hosted Android emulator. It sends a real
30-frame H.264 access-unit vector through the production Beacon QUIC session and media protocol
to the APK's sole production StreamCore and MediaCodec path. The test proves that at least two
different nonblank frames reach the activity's `SurfaceView` and that rendered-frame feedback
returns over the authenticated Beacon connection.

The fixture is not a runtime backend, server mode, compatibility transport, descriptor-file
path, or fallback. No fixture code is packaged in the production APK or StreamWorker.

## Rejected Alternatives

### Reuse The Local Windows Emulator Harness

The existing full-session harness remains useful for final Windows host acceptance, but another
task currently owns the local ADB server and emulator. Depending on that shared mutable resource
would make ordinary CI incomplete and would not provide an isolated regression gate.

### Run The Full StreamWorker On Ubuntu Or Android

The production Worker intentionally owns Windows Graphics Capture, D3D11, NVENC, named pipes,
and Windows certificate storage. Making that process cross-platform solely for a test would add
inactive production abstractions and weaken the Windows ownership boundary.

### Send Media Through Java, HTTP, UDP, Or A Mock StreamCore

Any of these would bypass the Beacon QUIC handshake, certificate pinning, native frame assembly,
or the production decoder path. A green result would not prove the required architecture.

## Protocol-Neutral Extraction

The server-side session state machine and media packetizer are protocol primitives currently
compiled inside the Windows Worker. They must be made platform-neutral before the fixture is
added:

- `ServerSessionProtocol` owns framed session, input, and feedback parsing plus generation and
  selected-plan enforcement.
- `IStreamTicketAuthorizer` is the narrow authorization dependency consumed by that state
  machine. The Windows `AuthorizedQuicTicketStore` remains the sole production implementation.
- `VideoMediaPacketizer` accepts an immutable encoded-access-unit view instead of an NVENC type.
  NVENC remains Worker-owned; packet framing belongs to the shared Beacon protocol.
- These primitives live in `Beacon.StreamProtocol`, compile on Windows and Android, and retain
  one implementation used by both the Worker and the acceptance endpoint.

The extraction must preserve the current protocol bytes and Worker behavior. Existing Worker
tests move with the implementation or continue against it through the same public contract.

## Test-Only Endpoint

An Android-native executable under `tests/` owns one MsQuic listener for one acceptance run. It:

1. loads an ephemeral PEM certificate and key generated by the CI script;
2. authorizes one ephemeral ticket through a test implementation of
   `IStreamTicketAuthorizer`;
3. uses `ServerSessionProtocol` for authentication, exact selected-video binding, start, stop,
   and rendered-feedback parsing;
4. parses the existing 640x360 H.264 `.bau` vector into complete access units;
5. uses `VideoMediaPacketizer` for production datagram framing;
6. sends the first configured IDR after an accepted start;
7. sends each following access unit only after rendered-frame feedback for the preceding frame;
8. exits after an accepted stop and emits evidence for authenticated start, sent frames,
   rendered feedback, and clean disconnect.

The endpoint does not expose settings, choose policy, emulate capture, or implement an alternate
client. It is a deterministic wire fixture around the production protocol boundary.

## Android Acceptance Test

The instrumentation test launches `BeaconActivity` and uses its real stream `SurfaceView`. It
constructs the normal `BeaconStreamCore`, `BeaconVideoPipeline`, `AndroidMediaCodecFactory`, and
feedback bridge with the ephemeral grant supplied by the CI script.

Rendered-frame callbacks trigger Android `PixelCopy` requests against the `SurfaceView`.
Success requires:

- authenticated StreamCore start with the exact H.264 SDR 640x360@30 plan;
- at least two rendered frame sequences;
- successful `PixelCopy` results;
- nonblank pixel evidence;
- different pixel checksums from different rendered frames;
- rendered-frame feedback accepted by the endpoint;
- explicit StreamCore stop and deterministic release of the decoder, activity, and endpoint.

All completion is event-driven. There are no startup sleeps, polling-readiness loops, or
wall-clock cancellation timeouts. Transport loss, decoder failure, PixelCopy failure, and
endpoint exit release the same acceptance waiter with a typed failure.

## CI Orchestration

The hosted emulator script generates an ephemeral certificate and ticket, computes the SPKI
SHA-256 pin, and pushes only the endpoint executable, MsQuic library, certificate, key, and H.264
vector into the emulator's temporary test directory. It starts the endpoint and waits for its
readiness marker through the process output stream, invokes only the exact acceptance
instrumentation method with grant facts, waits for both processes to finish, validates their
evidence, and removes the temporary files.

The existing device-local instrumentation suite continues to run independently. No local ADB
server, phone, Windows display, Apollo installation, or third-party streaming product is read or
controlled.

## Verification Contract

Static validation must prove:

- one shared server session protocol and one shared media packetizer implementation;
- the Windows Worker uses those shared primitives;
- the endpoint exists only under tests and is absent from shipped artifacts;
- no compatibility runtime, alternate Android stream path, or descriptor-file route appears;
- no fixture credential or private key is committed.

Dynamic validation must prove:

- all existing native, managed, Client Lab, Android JVM, and device-local instrumentation tests
  remain green;
- the test-only endpoint and production StreamCore complete an authenticated QUIC session;
- MediaCodec renders changing H.264 frames into the activity `SurfaceView`;
- rendered feedback crosses the production feedback stream;
- stop and teardown complete without a leaked endpoint, native handle, decoder, or activity.

This acceptance closes the hosted wire-to-screen gap. The separate Windows harness remains the
authority for WGC, NVENC, display ownership, application launch, reconnect, and physical restore.
